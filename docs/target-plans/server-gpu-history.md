# 目标计划：服务器 GPU 三天历史曲线

## 状态

- 目标 ID：`server-gpu-history`。
- 状态：执行中，当前批次 `history-006`。
- 启动条件：当前恢复基线和 UI 契约修复完成后，由目标模式切换到本计划。
- 证据状态：设计目标；真实服务器采样、性能和连续三天留存均为 `needs field verification`。

## 目标

在服务器状态页增加可展开的最近三天 GPU 历史视图，同时保留当前紧凑卡片布局：

1. 每张 GPU 卡对应一个独立曲线图，在同一百分比坐标轴叠加 GPU 利用率和显存利用率。
2. 服务器状态页增加总体曲线图，每台服务器一条曲线，显示每个时间桶内该服务器所有 GPU 的最高 GPU 利用率。
3. 服务器数量变化时自动分配稳定颜色；新增服务器不应导致已有服务器颜色无故变化。
4. 曲线颜色必须有足够区分度；服务器数量超过仅靠颜色可可靠区分的范围时，同时使用线型和点形状区分。

## 数据契约

- 复用现有 GPU snapshot 作为原始数据源，不建立第二套采集命令。
- Agent 侧复用本机 GPU snapshot，每分钟最多记录一次，生成三天滚动历史；每条曲线最多 `4320` 个真实采样点，最多保留 `128` 条历史序列，查询返回前继续按界面预算降采样。
- 每卡时间点至少包含 `serverId`、`gpuId`、`timestamp`、`gpuUtilPercent`、`memoryUsedMb`、`memoryTotalMb` 和 `memoryUtilPercent`。
- 总体曲线的服务器峰值定义为同一时间桶内全部 GPU 的 `gpuUtilPercent` 最大值；悬停详情同时显示峰值卡号和服务器 GPU 数量。
- 查询层以 `0` 补齐三天窗口内的缺失桶并标记 `imputed: true`，用于电脑关机或 Agent 停止期间连接完整曲线；补值不写回原始历史，界面明确说明其不代表真实负载。
- 历史存储必须有 `72 h` 时间边界、点数上限、原子写入和损坏恢复；不得无限增长。
- 查询 API 支持服务器、GPU、起止时间和最大点数，并在返回前执行服务端降采样。

## 界面设计

- 总体曲线放在服务器状态页顶部，默认折叠；展开后显示图例、时间范围和最近更新时间。
- 每张 GPU 卡保留现有摘要；卡片中的“历史”控件展开该卡曲线，不新增常驻大卡片。
- 单卡固定使用两种语义色：GPU 利用率与显存利用率在所有卡片中保持一致；悬停显示百分比及显存 MB。
- 总体图按稳定 `serverId` 分配颜色，图例显示服务器名称；断连服务器保留原颜色。
- 图表适配 VS Code 明暗主题、窄侧栏和高 DPI；文本、图例、悬停层不得遮挡相邻内容。
- Canvas 图表必须提供等价的文本摘要和键盘可访问的图例，不以颜色作为唯一状态表达。

## 配色算法

- 为服务器维护持久化的 `serverId -> color/lineStyle/marker` 映射，删除服务器时不立即复用其颜色。
- 从满足明暗主题对比度的 OKLCH 候选集中，使用最大化最小色差的方式选择下一颜色。
- 分配前校验新颜色与已用颜色的感知色差；低于阈值时改变线型和点形状，不生成近似颜色冒充可区分配色。
- 配色结果必须确定性可复现，并覆盖服务器新增、重命名、排序变化、临时离线和重新连接。

## 集成边界

- 历史遥测属于运行状态，不写入 `experiments/results.csv`、实验归档、Plan 归档、论文证据或 PPT 绘图契约。
- 不改变 SimpleSFTP 职责，不增加 SSH/SCP/rsync 路径，不自动修改 Xshell 会话。
- Webview 状态只传输当前可见时间范围和降采样结果，避免三天原始数据随每次实时刷新重复发送。
- 实时最新点与历史查询需要去重，防止同一时间桶重复绘制。
